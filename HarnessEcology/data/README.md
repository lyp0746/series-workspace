# 数据说明

## 是什么

全部数值是 GitHub 仓库搜索接口 `/search/repositories` 的 `total_count`（命中总数），
不是抽样、不是估计。查询串、返回计数、抓取时刻与原始 JSON 都在 `data/raw/` 与 `data/counts.json`。

快照日：**2026-10-23**。计数是活数据，重跑会得到略大的数。

## 口径

- **期段**：按 `created` 区间分桶。`pre` 行的天数是名义分母，**日均不给数**。
- **分辨率**：`stars:>=k fork:false`（k = 1/10/100/1000），另报不设门槛的全量。
- **存活率**：`pushed:>=2026-10-16`（近 7 天有推送）÷ 队列总量。所有队列的建仓窗口都在这天前至少 7 天结束。
- **交集**：`topic:dsh-plugin topic:agent-skills`；Jaccard = 414 /(22,001 + 35,894 − 414) = 0.7%。

## 已知偏差（写进正文，不在这里悄悄处理）

1. **事后贴标**：topic 可在任意时刻被加上，`created_at` 不会改。按 `created` 分桶得到的是出生史，不是入籍史。
2. **删除与私有化**：已删除仓库不在计数里，越早期段被删掉的比例越高。
3. **星标的时间不对称**：★≥k 需要时间积累，越新的仓库越吃亏；方向确定，幅度未知。
4. **短尾月**：10 月只统计到 23 日，一律换算日均。
5. **分项之和 ≠ 总量**：分批抓取期间活数据在增长，五个期段之和 22,004 vs 总量 22,001。

## 一条被放弃的路径（保留作记录）

逐仓库抽样试过两次，都失败：

- 第一次用默认相关度取前 200 条 → "零星仓库占比 0%"、"近 7 天有推送 100%"；
- 第二次改用 `sort=created` → 无效，该接口不接受 `created` 作为排序键，退回默认相关度。

原因：仓库搜索只支持按 `stars / forks / updated` 排序，任何 `page` 抽样都落在热门/活跃仓库上。
所以最终改用 `total_count`（不受排序污染）。这条经验构成正文 F4。
